# 魔程化解研发管理工具 · 业务闭环与菜单关联评估报告

> 评估日期：2026-11-14
> 评估范围：系统性、全面性、管理逻辑闭环、菜单关联性（业务视角，非代码测试）
> 评估对象：F:/WorkBuddy/2026-10-31-19-11-31（app 前端 + docs 业务文档）
> 取证方式：只读静态审查（路由/菜单定义、视图组件、116 个 domain 引擎、PRD/产品核心定义/功能说明/差距分析等业务文档）

---

## 一、结论速览

| 维度 | 结论 | 一句话判据 |
|---|---|---|
| 系统性 | ✅ 成体系 | 围绕「审批驱动阶段门禁」主轴，20 组菜单、116 引擎分层清晰、单向依赖 |
| 全面性 | 🟡 基本齐全，边界漂移 | 汽车电子研发管理域覆盖完整，但存在「通用 PM vs 研发域」定位摇摆导致的边界模糊 |
| 管理逻辑闭环 | 🟡 主干已闭环，末端有断点 | 立项→门禁→交付主轴闭环真实；但若干环节「有引擎、无页面承接」或「有页面、无导航串联」 |
| 菜单关联性 | 🔴 偏弱，是主要短板 | 数据层已打通（84/90 视图共享 store），但页面级导航关联极少（仅 5 视图含跳转），大量「应关联」菜单未串联 |

**总体判断**：这是一个「业务规则引擎极强、数据闭环基本成立，但**操作路径 / 菜单导航关联明显不足**」的工具。核心管理逻辑的判定（分级、门禁、追溯、挣值）真实可算且闭环，但从用户视角看，**菜单之间的"下一步去哪"是断的**——这与你关注的"哪些菜单没有形成关联"直接对应。

## 二、系统性评估（围绕核心主轴是否成体系）

### 2.1 核心主轴清晰

产品定义（`docs/PRODUCT-CORE-DEFINITION.md`）确立六条不可动摇原则，作为全系统统一主轴：

1. 流程管控为本（不是任务看板/甘特图）
2. 审批驱动门禁（批准才能进入下一阶段）
3. 四段式审批链（发起→审核→会签→批准）
4. 阶段+交付物双重管控
5. 全留痕可追溯（15 年档案）
6. 合规级归档（哈希防篡改 + 只读）

### 2.2 分层架构清晰

- **业务规则层**：116 个纯函数 domain 引擎（分级 grading、门禁 gate、追溯 trace、挣值 evm、变更 change、风险 risk、合规 compliance、审批绑定 approvalBinding 等），零框架依赖，判定逻辑单一权威。
- **编排层**：全局 store（app.ts，4520 行）串联引擎，`runGate` 接收控制点结果 + 基线冻结 + 安全签署判定。
- **展示层**：20 组一级菜单 / 110 个二级页面。

### 2.3 控制点判据真实取数（正向证据）

`controlPoints.ts` 依赖 trace/schedule/evm/change/risk/compliance 六大引擎，48 控制点判据从真实业务数据取数，**非静态 flag 摆设**——这是"管理逻辑可复算"的扎实证据。

1. **定位摇摆**：产品经历了「研发域垂直平台 → 研发流程管控工具 → 通用 PM 工具 + 研发域插件」三次定位演变。当前菜单仍是**研发域为主**，与最新"通用 PM 工具"定位存在张力——`PROJECT-PROPOSAL-GENERIC-PM.md` 提出的"看板/自定义字段/轻量任务模式"三大通用能力**尚未落地**（菜单里无看板视图、无自定义字段配置）。
2. **文档数字失实**：功能说明页称"19 模块 / 96 页面 / 60+ 引擎"，实际是 20 菜单 / 110 页面 / 116 引擎，文档滞后。

## 四、管理逻辑闭环评估（各链条是否闭环）

### 4.1 已闭环的主干链条（正向）

| 闭环链条 | 闭环方式 | 证据 |
|---|---|---|
| 立项→门禁→交付 | 立项申请五分级→评审→主计划→Gate1-5→OTS→PPAP→SOP | controlPoints 取数 trace/schedule/evm/change/risk/compliance |
| 审批→门禁 | approvalBinding 绑定 flowEngine+stageTemplate+deliverableApproval | `未批准不得进入下一阶段`引擎级阻断（gateEnforce） |
| 需求→追溯→变更 | 五类链路 L1-L5 + 闭包表双写 + 断链四类 | change.ts 影响闭包 ≤6 跳 |
| 数据→报表 | 驾驶舱与业务同源 | store 派生数据 computed |
| 门禁→审计→归档 | 每次审批存档 + prev_hash 哈希链 | audit.ts append-only + guardImmutable |

### 4.2 存在断点/弱关联的链条（需关注）

| 断点 | 现象 | 影响 |
|---|---|---|
| 页面导航断 | 90 视图仅 5 个含 router.push，跳转目标仅 7 个 | 用户完成一步后无"下一步"引导 |
| 齐套→Gate 弱提示 | kitting 引擎有齐套率计算，但试制页到 Gate 无直接跳转 | 齐套不通过时用户需自行找到 Gate 页 |
| 交付物→Gate 弱提示 | 交付物清单缺件阻断 Gate（C-19），但两菜单无导航关联 | 缺件时无引导跳转 |
| 问题/风险→PDCA→经验库 | 三个菜单独立，无"处置后转 PDCA、复盘后入经验库"的流转 | 质量闭环靠人工串联 |
| 会议决议→任务 | 决议条目化转任务（COM-007）机制存在，但无页面级跳转 | 决议转任务需手动 |

## 五、菜单关联性评估（核心短板）

### 5.1 数据层关联 vs 导航层关联

| 层 | 现状 | 判定 |
|---|---|---|
| 数据层 | 84/90 视图引用全局 store，业务数据单一权威、共享 | ✅ 已打通 |
| 导航层 | 仅 5 视图含跳转，绝大多数菜单无"关联跳转" | 🔴 明显不足 |

### 5.2 已建立的菜单关联（仅有）

| 来源菜单 | 关联目标 | 方式 |
|---|---|---|
| 图纸与 EBOM | ECR/ECN 变更 | 按钮「发起 ECR 变更」 |
| 项目台账 | 立项申请 | 按钮「立项申请」 |
| 项目台账 | 评审与门禁 | 按钮「查看」 |
| OTS 认可 | 附件 A/B/C | 三个附件按钮 |
| 项目主计划 | 主计划编辑器 | 模板跳转 |
| 主计划编辑器 | 项目主计划 | 保存后跳转 |

### 5.3 应关联但未关联的菜单（整改建议清单）

| # | 应建立关联的菜单对 | 缺失的关联 | 建议 |
|---|---|---|---|
| 1 | 齐套校验 ↔ 评审与门禁 | 齐套不通过时无"去门禁查看" | 齐套页加"影响的门禁"提示 + 跳转 |
| 2 | 交付物清单 ↔ 评审与门禁 | 缺件阻断时无引导 | 缺件清单列出阻断的 Gate + 跳转 |
| 3 | 需求条目库 ↔ 追溯与覆盖率 | 条目化后无"查追溯" | 需求页加"断链下钻"入口 |
| 4 | 图纸与 EBOM ↔ 齐套校验 | EBOM 冻结后无"试制齐套" | EBOM 页加"查看齐套" |
| 5 | 问题管理 ↔ PDCA 闭环 | 问题处置后无转 PDCA | 问题关闭后提示生成 PDCA 条目 |
| 6 | 复盘与经验库 ↔ 会议与决议 | 复盘结论无转决议/任务 | 经验条目化转任务 |
| 7 | 风险台账 ↔ 评审与门禁 | 高 RPN 风险无"影响门禁"提示 | 红区风险列出受影响 Gate |
| 8 | 成本偏差 ↔ 四值与挣值 | 两菜单复用同组件但无互跳 | 偏差页加"挣值明细"链接 |
| 9 | 供应商管理 ↔ 样件试制 | 定点未闭环无"影响开工"提示 | 未定点供应商阻断试制时提示 |
| 10 | 主计划 ↔ WBS 与任务 | 主计划到 WBS 无跳转 | 主计划节点下钻到 WBS |

### 5.4 菜单复用导致的"假关联"风险

以下菜单**共用同一个视图组件**，但菜单名不同，存在"菜单名 vs 实际功能不符"的风险，用户可能误以为是独立功能：

| 组件 | 复用菜单 | 风险 |
|---|---|---|
| EvmView | 成本偏差 / 工时归集 / 四值挣值 / 供需超分配（4 处） | 4 个不同菜单打开同一挣值页，功能边界模糊 |
| ApprovalsView | 我的待办 / 发起流程 / 待我审批 / 流程监控（4 处） | 4 个入口同页，差异靠参数区分 |
| RiskView | 风险管理 / 风险台账 / 漏洞台账（3 处） | 风险与漏洞台账同页 |
| DocView | 文档库 / MDR 齐套 / 会签工作台（3 处） | 文档库与齐套、会签同页 |
| PortalView | 项目门户 / 送审件 / 会议决议（3 处） | 门户与送审、会议同页 |

## 六、综合结论与建议

**结论**：系统性 ✅、全面性 🟡、闭环性 🟡、菜单关联性 🔴。

这是一个「业务规则引擎与数据闭环已经很强，但**用户体验层的菜单关联/导航引导明显滞后于业务深度**」的工具。核心判定逻辑（分级、门禁、追溯、挣值、合规）真实可算且闭环，但用户"从一个菜单走到下一个相关菜单"的路径是断的，主要靠人工记忆和全局 store 的数据共享来"隐性关联"。

### 优先整改建议（按价值排序）

1. **补齐菜单导航关联**（最高价值、最低成本）：为 §5.3 清单里的 10 对"应关联菜单"补跳转/提示，让闭环从"数据闭环"升级为"操作闭环"。
2. **收敛菜单复用**：将 EvmView×4、ApprovalsView×4 等复用组件按菜单语义拆分或加明确的页内 Tab/锚点，消除"菜单名≠功能"的歧义。
3. **对齐产品定位**：明确当前是"研发域工具"还是"通用 PM 工具"，若走通用路线，补齐看板/自定义字段/轻量任务模式三大缺失能力。
4. **修正文档口径**：功能说明页、README 的模块数/页面数/引擎数需与实现对齐（19→20、96→110、60+→116）。
