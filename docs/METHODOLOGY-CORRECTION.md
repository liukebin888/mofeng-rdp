# 方法论纠正报告：实现方决策职责的归位

> 文档编号：MOFENG-RDP-METHOD-001
> 日期：2026-11-02
> 性质：对既有决策清单 / 差距分析中「把专业判断外包给需求方」这一根本性方法错误的纠正。

---

## 1. 错误定性

此前把「实现方的专业判断义务」错误地转移给了需求方/客户，具体表现为：

**错误模式**：提出问题 → 等需求方拍板 → 才能往下做。

**正确模式**：实现方先给出完整方案 → 做完 → 交付测试评估 → 给出「是否符合」的结论。

这是一处**影响项目成败的严重错误**。对复杂管理工具软件，需求方要的是**结果与结论**，不是一串选择题。客户不会、也不应替实现方决定「CRM 是不是子模块」「主数据怎么来」「试点怎么组织」「是否四线并行」「变更同步是否一类风险」——这些恰恰是实现方凭行业专业（APQP / PPAP / ISO 16949 / 等保 / 密评）应当自行给出的判断。

最典型的反例即**等保/密评**：正确逻辑是「把系统做完整 → 提交测评 → 得出是否符合的结论」，而不是「未发布先要求证明可行、等客户选定机构才能开工」。测评是交付后的验证环节，不是开工前的前置卡点。

---

## 2. 错误根因

| 根因 | 说明 |
|---|---|
| 把「决策」与「执行」混为一谈 | 把本应实现方直接按行业标准执行的项，包装成「待需求方拍板的决策项」 |
| 把「验证」前移为「前置条件」 | 测评、试点、合规证明都是「交付后的验证」，被误置为「开工前的卡点」 |
| 把「采购细节」升级为「项目阻塞」 | 机构选定、法人圈定等采购/行政细节，被误当技术阻塞 |
| 风险厌恶外化 | 用「等客户确认」来规避实现方本应承担的专业判断责任 |

---

## 3. 逐项纠正对照

| 决策项 | 原错误逻辑 | 正确逻辑（实现方自持） |
|---|---|---|
| **D-04 主数据权威源** | 等客户 IT 书面确认 | 实现方按 15.1 矩阵自行定义权威源，PLM/ERP 自行定义通讯协议模拟，人员从内部模块提取 |
| **D-07 等保/密评** | 等客户选定测评机构才能开工 | 实现方按等保三级（GB/T 22239）/ 密评（GB/T 39786）要求把系统做完整 → 提交有资质机构测评 → 得出「符合/不符合」结论；机构选定是采购执行细节，非前置卡点 |
| **D-10 在研项目清单** | 等客户提供存量项目清单 | 在研项目是立项流程产物（立项→审批→下达任务书→建立），非外部存量；迁移仅限主数据，骨架随试点由实现方构建 |
| **D-11 CRM/报价** | 问客户是否有 CRM | CRM/报价是平台内子模块，实现方 P1 自行交付 |
| **D-12 试点范围** | 等客户圈定法人 | 试点是功能模拟测试，范围由实现方自行规划 |
| **D-13 四线并行** | 问需求方「是否四线并行」 | 汽车零部件研发「结构/硬件/软件/工艺」四线并行是 APQP 标准行业实践，实现方**直接按四线并行设计**并处理接口传导 |
| **D-16 变更同步** | 问需求方「是否列一类风险」 | 变更管理（ECR/ECN）在 APQP/16949 中本就是一类核心风险，实现方**直接按一类风险管控** |
| **D-08 AI 场景** | 纠结三类裁剪、反复走 SRS 变更评审 | 实现方直接给出「六类场景完整方案 + 境内租用 + 数据不出境」默认方案并做完 |

## 4. 正确的工作原则（此后执行）

1. **实现方先给方案**：每项一律先由实现方按行业标准给出可执行的默认方案，而非提问。
2. **验证后置**：测评、试点、合规结论都是「交付后的验证环节」，不得前置为开工卡点。
3. **采购分离**：机构选定、法人圈定等行政/采购细节与技术改造解耦，不阻塞开发。
4. **行业惯例即默认**：四线并行、变更管控、主数据权威等有 APQP/PPAP/16949/等保明确惯例的，直接采用，不问需求方。
5. **需求方只做两类事**：(a) 确认范围/商务边界（如预算、交付窗口）；(b) 验收结论。技术判断一律由实现方承担。
