# 架构方案：通用项目管理工具（多实例独立部署 · 万级规模）

> 项目：MOFENG-RDP 通用项目管理工具
> 文档：PROJECT-PROPOSAL-GENERIC-PM
> 版本：v2.0（2026-11-03，定位纠偏后重出）
> 状态：待评审
> 前因：上一版方案把平台定位为「研发域垂直平台 + SaaS 多租户」，经澄清，正确定位为「通用项目管理工具 + 多实例独立安装 + 独立数据库」。

---

## 0. 定位纠偏（重要，先对齐再谈架构）

| 维度 | 原理解（已纠正） | 正确定位 |
| --- | --- | --- |
| 产品性质 | 研发域交付保证垂直平台 | **通用项目管理工具**，不绑定行业/用户画像 |
| 用户模型 | 一套系统内多租户共享 | **多实例独立安装**：像 CAD 软件，各客户各自安装、各自使用 |
| 数据隔离 | SaaS 多租户逻辑隔离 | **独立数据库**：每个安装实例一个独立数据库，实例间物理隔离 |
| 规模指标 | 多租户路由下并发 | **单实例内 10000 人 / 5000 人同时在线**的容量与性能 |
| 研发域能力 | 核心定位 | **可选插件**：底座之上按需启用（闸门/证据链/BOM 等） |

**一句话定位**：一套可独立安装的通用项目管理软件，每个组织装一套、用一个独立库；核心是通用项目管理（计划/任务/资源/协作），研发域特性作为可选插件按需开启；单实例需扛住 1 万人规模、5000 人同时在线的性能要求。

## 1. 现状盘点（架构级事实）

### 1.1 后端技术栈（已具备，可承载万级）

| 层 | 技术 | 现状 | 万级评估 |
| --- | --- | --- | --- |
| 框架 | Spring Boot 3.2.5 + 标准 DDD 四层（domain/application/infrastructure/boot） | 已成型 | ✅ 可承载 |
| 持久化 | MyBatis-Plus + MySQL 8 + Flyway | 已成型 | ✅ 需容量调优 |
| 缓存 | Redis（缓存/会话/限流/分布式锁） | 已接 | ✅ 关键 |
| 检索 | Elasticsearch（全文/大列表） | 已接 | ✅ 关键（万级列表） |
| 异步 | Kafka（领域事件/异步任务） | 已接 | ✅ 削峰 |
| 连接池 | HikariCP | **pool-size=20（dev 值）** | ⚠️ 需按万级调优 |
| Web 容器 | 默认 Tomcat（spring-boot-starter-web） | 默认 | ⚠️ 需调线程池/连接数 |

**结论**：技术栈本身已能支撑万级，缺的是「容量规划 + 性能工程 + 压测基线」，而非重构。

### 1.2 前端能力分类（底座 vs 插件）

| 分类 | 现有分组 | 性质 |
| --- | --- | --- |
| **通用底座** | 工作中心、项目计划与进度、资源与成本、门户与协同、文档中心、流程中心、成本管理 | 通用项目管理，各行业通用 |
| **研发域插件** | 项目前期（分级/报价）、研发过程（需求/追溯/EBOM/ECR/门禁/基线/软件版本）、样件试制、交付管理、质量管理、供应链协同（APQP/PPAP/8D） | 研发域专属，应可配置启用 |

## 2. 规模目标拆解（5000 在线 / 10000 人）

### 2.1 指标定义

| 指标 | 目标值 | 说明 |
| --- | --- | --- |
| 总用户数 | ≤ 10,000 | 注册用户总量（独立实例内） |
| 并发在线 | 5,000 | 同时在线（建立会话/连接） |
| 活跃操作并发 | 500~1,000 TPS | 在线≠同时请求，按 10%~20% 活跃率估算 |
| P95 延迟 | < 500ms（普通查询）/ < 200ms（缓存命中） | 交互体验 |
| 可用性 | 99.9% | 月宕机 < 43 分钟 |

### 2.2 容量模型（粗算，供评审校准）

```
5000 在线 → 活跃请求并发 ≈ 5000 × 20% = 1000 TPS（峰值）
  ├─ 读（80%）800 TPS → Redis/ES 命中，DB 只承担 20% 穿透 ≈ 160 TPS
  ├─ 写（20%）200 TPS → MySQL 主库，需批量/异步削峰
  └─ 实时协作（看板/审批）→ WebSocket 长连接 5000 条，需独立网关/连接管理
```

### 2.3 分层容量设计

| 层 | 万级配置 | 关键点 |
| --- | --- | --- |
| Web 容器 | Tomcat 线程池 maxThreads 200~400；或换 Undertow 降内存 | 连接数 vs 线程数解耦 |
| 连接池 | HikariCP pool-size 50~100（按 DB 核数），min-idle 20 | 当前 20 是 dev 值，需按部署规格覆盖 |
| MySQL | 主从读写分离；慢查询优化；分区表（审计/日志类大表） | 写 200 TPS 主库可扛，读走从库/缓存 |
| Redis | 会话+热点缓存+限流+分布式锁；内存按 10 万 key 估算 | 集群模式预留 |
| ES | 大列表/全文检索走 ES，避免 DB 大表扫 | 万级列表分页不卡 |
| Kafka | 异步任务（通知/报表/审计落盘）削峰 | 写路径解耦 |

## 3. 通用底座 + 研发域插件化设计

### 3.1 底座（本期重点补齐）

现有「计划/任务/资源/协作/文档/流程」已是通用能力，需补齐的通用项：

| 缺口 | 说明 |
| --- | --- |
| 看板/Kanban 视图 | 通用任务管理标配（列表/看板/甘特三态） |
| 自定义字段与表单 | 不同行业/团队的项目字段不同（Jira 式自定义） |
| 组织与团队模型 | 通用「组织→团队→项目」而非研发域「专业线」 |
| 简单任务模式 | 小团队无需 CPM/挣值/门禁，一个轻量模式即可用 |

### 3.2 插件化机制

研发域能力（闸门/证据链/BOM/控制点/APQP）作为**可选插件**：

| 机制 | 方案 |
| --- | --- |
| 插件开关 | 实例级配置 `feature.enable.rdp=false`（默认关），开启后研发域菜单/引擎/流程生效 |
| 引擎复用 | TS 纯函数引擎已模块化，插件开关只控「入口 + 数据表」，引擎本身不改 |
| 数据隔离 | 插件关闭时研发域表不建/不查，通用表不受影响 |

**近期策略（你已拍板）**：暂不动已有研发域功能，先补通用能力。插件化作为中期演进，本轮只做「能力分类清单」标注，不做代码重构。

## 4. G1 空间切换器的处理建议（先出方案再定）

### 4.1 现状回顾

G1 已实现「同租户内多项目组合切换」（演示科技有限公司/示例电子有限公司），语义是「一个实例内按项目组合组织项目」。

### 4.2 与新定位的对照

| 结论 | 说明 |
| --- | --- |
| 保留价值 | 单实例内「项目组合/项目集」仍是通用项目管理的有用组织维度（大集团内多 BU 多项目集） |
| 不冲突 | 「多实例独立部署」解决的是「客户间隔离」，「项目组合」解决的是「客户内组织」，两者是不同层级，**互不矛盾** |
| 需调整 | 去掉「租户」概念在 UI 的暴露（独立部署后无多租户），空间=项目组合直接作为组织维度 |

### 4.3 建议（待你最终拍板）

**建议保留 G1 空间切换器，语义收敛为「项目组合（Portfolio）」**——它不违反"独立安装"模型，反而是通用项目管理（多项目集管理）的标配能力。仅需后续把「租户」从用户可见概念中淡化为「实例本身」。
