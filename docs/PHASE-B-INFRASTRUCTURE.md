## 0. 设计者立场：阶段 B 做什么、不做什么

阶段 A 已把最难、最值钱的**业务规则**（70 引擎 / 744 例）收口为框架无关的纯函数权威。阶段 B 的唯一任务是：**给这套规则配上能扛住规模约束的运行载体**，并守住合规底线。

**做什么**：
1. 数据层从 JSON 文件 → MySQL 8（事务、索引、追溯闭包表、分区归档）
2. 会话/缓存/限流 → Redis
3. 检索 → Elasticsearch 8
4. 异步/事件 → Kafka
5. 传输加密 → 国密网关（SM2/SM3/SM4）
6. 等保三级 + 密评 → 系统做完整后提交测评（验证后置）

**不做什么**（避免重蹈「执行者」覆辙）：
- 不重写领域规则。TS 纯函数引擎是规则唯一权威，Java 领域层以「通过同一套 744 例测试」为迁移完成判据。
- 不在开工前等任何外部确认。基础设施选型 SRS 已锁定（ARC-021），直接落地。
- 不把「测评机构选定」当阻塞。测评是交付后验证，机构选定是采购执行细节，与技术改造解耦。

## 1. 核心架构决策（设计者结论）

### 1.1 分层补全，而非推倒重来

SRS ARC-001 四层架构的权威映射：

| 层 | SRS 要求 | 当前实现 | 阶段 B 动作 |
|---|---|---|---|
| 表现层 | Vue 3 + TS + Element Plus | ✅ 已完成（56 视图） | 保持，仅随应用层接口微调 |
| 应用层 | Controller + ApplicationService + Flowable | ❌ 缺（Node 零依赖混做） | **补 Java 应用层**（Spring Boot 3.2.5） |
| 领域层 | 禁止依赖 Spring/MyBatis/HTTP | ✅ TS 纯函数引擎（70 个） | **保持 TS 权威，Java 侧以同测试验收迁移** |
| 基础设施层 | MySQL/Redis/ES/Kafka/对象存储 | ❌ 缺（JSON 文件） | **补基础设施**（按 ARC-021 清单） |

**关键洞察**：SRS 明确「领域层禁止依赖 Spring/MyBatis」，而当前 TS 纯函数引擎**恰恰满足这条**——它框架无关、可复算、已 744 例验证。阶段 B 不是「用 Java 重写规则」，而是**给规则补应用层编排 + 基础设施持久化**。

### 1.2 领域规则迁移的验收判据（防「两套规则各说各话」）

TS 引擎 → Java 领域层，迁移完成的**唯一判据**是：**用同一套 744 例测试用例跑 Java 实现，结果一致**。禁止出现「TS 一套规则、Java 一套规则」。

迁移策略（三选一，推荐 b）：
- (a) 手写 Java 翻译 TS 引擎 → 成本高、易漂移
- (b) **GraalVM / TeaVM 复用 TS 引擎** → 复用同一权威，零漂移（推荐）
- (c) 领域规则继续跑在 Node 侧，Java 仅做应用编排 + 基础设施 → 两进程，短期可行

> 设计者倾向 (b)，但 (c) 是「不推倒重来」的务实起点：先用 Java 补应用层 + 基础设施，领域规则短期仍由 Node/TS 侧承载，用「通过同一套测试」作为逐步迁移的护栏。

### 1.3 模块化单体（R1 不做微服务）

SOLUTION 12.2 已裁定：**R1 单一部署单元，模块化单体**。核心理由是 K5「四类断链合计为 0」依赖「写需求 + 写追溯关系」的本地事务原子性——微服务的跨服务窗口必然产生断链，K5 无法恒为 0。这条推理是硬约束，不是「省事」。

### 6.2 迁移模式（可复用于其余 69 引擎）

1. **值对象先行**：把 TS 的 `enum`/`interface` 拆成独立 Java `enum`/不可变值对象（如 `Asil`/`SelfDev`/`Level`），保持语义同构。
2. **真值表即权威**：`GRADING_ROWS` 用 `List.of(...)` 逐行一一对应 TS 数组，`Predicate<NormalizedInput>` 承接 `match` 函数，**顺序即优先级，命中即返回**——守住 CLS-002「只允许查表」铁律。
3. **裁定规则独立**：`validate()` 产出 6 条 `Check`（code/name/ok/note），与定级解耦，用于发现口径冲突与越级。
4. **留痕可复算**：`snapshotHash` 用 JDK 内置 SHA-256，与前端 `hashOf` 语义对齐（确定性、可逐位复算）。
5. **领域纯净性**：全部落在 `mofeng-domain` 模块，零框架依赖，由 `DomainLayerArchitectureTest`（ArchUnit）构建期守护。

### 6.3 迁移中修正的两个口径要点

- **CLS-005「分解不降级」方向**：`rank(level) <= rank(parentLevel)`（rank 越小管控越严）。父项目 L1、子项目判 L2（更松）→ **违反**，应 fail；同等级/更严才通过。初版测试断言写反，已按 TS 权威修正。
- **JDK 版本漂移**：pom 锁定 17，但本机只有 JDK 21。JDK 21 向后兼容编译 target 17，当前用 JDK 21 跑通；上线前需在 CI 锁定 JDK 17 镜像避免「17 编译、21 运行」的隐性漂移。

### 6.6 B4 Kafka 异步/事件落地结论（2026-11-02）

| 验收判据 | ARC-003：白名单外事件拒投递 + 事件溯源链连续；至少一次投递（Kafka acks=all）+ 消费端幂等（确定性 eventId/taskId 去重） |

**关键设计决策**：
1. **确定性 id 即幂等锚**：事件 eventId 与任务 taskId 均由「幂等键 + 聚合 + 载荷」SHA-256 派生，「同一业务事实只产生同一 id」，消费端以 id 集合去重，天然支撑至少一次投递下的幂等。
2. **租户上下文显式传递**：异步跨线程/进程，租户不依赖线程局部，随消息头显式传递；`AsyncTaskEngine.checkSubmit` 兜底断言（缺失即 `TENANT_FORGED` 拒），与 `TenantContextHolder` 注入形成双重保障（TEN-004）。
3. **领域/基础设施边界**：白名单、幂等、溯源链、状态机判定全落领域层纯函数；Kafka 投递/订阅只做编排（Spring Kafka 序列化 + acks=all），复用领域判定，符合 ARC-001。

### 6.7 B5 国密网关 + 传输加密落地结论（2026-11-02）

**结论**：国密 TLS 套件判定引擎迁至 Java 领域层，国密网关配置抽象落基础设施层，SEC-012「协议扫描无弱套件、证书链与算法符合国密」判据可测；真实密评（NFR-010）验证后置。

| 项 | 内容 |
|---|---|
| 领域引擎 | `gmtls/GmTlsEngine`：国密套件判定（SM2/SM3/SM4 三要素）/ 弱套件检测（TLS1.2 以下 + RSA/AES 回落）/ 协议扫描汇总 / 证书链国密校验（SM2 双证书）/ 密钥分级轮换分离判定 |
| 基础设施 | `gateway/`：`GmTlsGateway` 抽象 + `NginxTongsuoGmGateway`（tongsuo 铜锁，SM2 双证书 + SM3 签名 + SM4 加密）；`resources/gateway/nginx-tongsuo-gm.conf` 配置模板 |
| 测试结果 | 领域层新增 12 例（GmTlsEngineTest），合计 244→256 例全过，backend 5 模块 BUILD SUCCESS |
| 验收判据 | SEC-012：协议扫描无弱套件（TLS1.2 以下 0 个）+ 证书链与算法符合国密；NFR-010 密评结论验证后置 |

**关键设计决策（边界职责，ARC-001）**：
1. **国密传输属网关层，非应用代码层**：SRS 第 23 章「国密网关位置=平台边界，统一卸载与卸载后再加密」；应用层不自行实现 SM2/SM3/SM4（自造既不安全也不合规），由边界网关（Nginx+tongsuo/商用密码机/云国密）卸载国密 TLS、向内以受控内网转发。
2. **判定落领域层、卸载落网关**：套件合规/弱套件/证书链/密钥管理判定落领域层纯函数 `GmTlsEngine`（可测、可复核协议扫描产物）；实际 TLS 终止与算法运算在网关。
3. **字段加密与传输加密两条线**：`cipher/CipherEngine`（字段级 XOR 流加密，SEC-013 基础）与 `gmtls/GmTlsEngine`（传输层国密套件判定，SEC-012）职责分离，不混淆。
4. **密钥分级轮换 + 物理分离**（NFR-010）：密钥不入库、分级≥2 级、轮换周期 1~365 天，由 `checkKeyManagement` 纯函数守护。
