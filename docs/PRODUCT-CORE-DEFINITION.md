## 0. 一句话定义

> 一套**按汽车零部件行业研发流程对项目进行有效管控**的管理工具。核心不是"进度跟踪"，而是**「审批驱动的阶段门禁 + 全流程留痕 + 15 年合规档案」**——帮助客户把「该谁、在哪个阶段、按什么次序、审核/会签/批准什么、留什么证据」这套管理动作，做成结构化、可执行、可追溯、可审计的闭环。

---

## 1. 产品核心（不可动摇的六条）

| # | 原则 | 说明 |
| --- | --- | --- |
| P1 | 流程管控为本 | 按汽车零部件行业研发流程分阶段管控项目，不是任务看板/甘特图 |
| P2 | 审批驱动门禁 | **每个申请、计划、任务、输出物都需审核批准；原则上只有批准了，才能实施下一阶段工作** |
| P3 | 四段式审批链 | 「发起 → 审核 → 会签（并行）→ 批准」贯穿每个阶段、不断重复 |
| P4 | 阶段+交付物双重管控 | 阶段过关需交付物齐套；交付物审批嵌入阶段审批 |
| P5 | 全留痕可追溯 | 每次审核批准都存档，作为档案**留存 15 年** |
| P6 | 合规级归档 | 哈希防篡改 + 只读归档，满足等保/审计标准 |

## 2. 核心机制模型

### 2.1 阶段模型（模板 + 可调）

内置汽车零部件研发阶段模板（类 APQP），客户可增删改：

```
① 立项/策划 → ② 产品设计与开发 → ③ 过程设计与开发 → ④ 试制与OTS验证 → ⑤ 量产与交付 → ⑥ 反馈与改进
```

- 阶段是**可配置**的：客户可在模板上增删阶段、改阶段名、调阶段次序。
- 阶段之间有**门禁（Gate）**：前序阶段未批准，后续阶段不可开展。

### 2.2 审批链模型（可配置 + 并行会签）

```
发起（发起部门提交）
  → 审核（审核人员，单人审核）
  → 会签（多个部门【并行】签字，全部通过才过关）
  → 批准（最终批准人）
```

- **可配置**：不同阶段/对象可配不同节点（有的仅"审核+批准"，有的"多级审核+多部门会签+批准"）。
- **并行会签**：会签节点内多部门并行签字，全通过才过关（对齐现有 `SignMode='all'`）。
- 每个节点都支持：通过 / 驳回 / 转办 / 加签 / 超时升级。

### 2.3 门禁原则（硬约束）

> 任何阶段/交付物的「下一阶段工作」，前置条件是「当前审批已批准」。

- 未批准 → 下一阶段任务/输出物**不可创建、不可实施**（引擎层阻断，非仅 UI 提示）。
- 现有 `gate.ts`（runGate + SOD 同人校验 + SLA 超时）是门禁的现有实现底座。

## 3. 管控对象全景（什么要审批）

| 对象类别 | 示例 | 审批链 |
| --- | --- | --- |
| 申请 | 立项申请、变更申请、样件申请 | 发起→审核→会签→批准 |
| 计划 | 项目计划、阶段计划、资源计划 | 发起→审核→批准（或+会签） |
| 任务 | 关键任务、试制工单、交付任务 | 发起→审核→批准 |
| 输出物 | 方案、图纸、EBOM、样件、报告、PPAP 文件 | 发起→审核→会签→批准 |

**共性**：每个对象都走「发起→审核→会签→批准」，且**每次审批都归档留存 15 年**。

## 4. 15 年合规归档设计

### 4.1 归档范围（全留）

- 每次审批的**结果 + 签字记录**（谁、何时、在哪个节点、批了什么、会签意见）
- 关键**输出物版本**（批准后的方案/图纸/报告/PPAP 文件的冻结版本）
- 过程留痕（驳回/转办/加签/超时的完整历史）

### 4.2 归档技术（合规级）

| 要求 | 实现 |
| --- | --- |
| 不可篡改 | 哈希链（现有 `verifyChain`）：每条审批记录哈希串联，改动即断链可检出 |
| 只读归档 | 已批准的档案进入只读态，禁止修改/删除（现有 `guardImmutable`） |
| 长期存储 | 数据库归档表 + 文件对象存储（冻结版本），15 年可查 |
| 合规审计接口 | 支持按对象/阶段/时间/人员检索完整审批轨迹，导出审计报表 |
| 保留期 | 档案保留策略 15 年，到期处理走合规流程（不自动删） |

### 4.3 与等保合规的关系

现有 `compliance.ts` + 国密 TLS + 审计链已是等保底座，15 年档案是等保「日志留存 + 审计追溯」要求的业务化落地。

## 5. 现有能力盘点（避免重复造轮子）

| 能力 | 现有资产 | 缺口 |
| --- | --- | --- |
| 可配置审批链 | `flowEngine.ts`（FlowDefinition + start/approve/sign/branch/end + 会签 SignMode） | ✅ 已有，需按「发起→审核→会签→批准」标准模板化 |
| 并行会签 | `flowEngine.ts` sign 节点 `SignMode='all'` | ✅ 已有 |
| 阶段门禁 | `gate.ts`（GATE_TEMPLATES + runGate + SOD + SLA） | ✅ 已有，需与阶段模型对齐 |
| 状态机 | `stateMachine.ts`（需求/项目/供应商/样件/ECR） | ✅ 已有 |
| 哈希审计 | `audit.ts`（appendAudit + verifyChain + guardImmutable） | ✅ 已有 |
| 文档/交付物 | `docEngine.ts` + `docAnnotation.ts` + 交付物清单 | ✅ 已有，需绑定审批+归档 |
| **阶段模板可配置** | 无 | ⚠️ 缺：研发阶段模板的增删改配置 |
| **「未批准不得实施」引擎级阻断** | 部分（Gate 阻断 OTS 等） | ⚠️ 缺：通用「前序未批准→后续禁做」的引擎级强制 |
| **15 年归档策略** | 部分（审计链 append-only） | ⚠️ 缺：明确的归档表/保留期/只读归档层 |

## 6. 通用底座 vs 研发域插件的边界（结合前一轮定位）

| 层 | 内容 | 说明 |
| --- | --- | --- |
| **通用底座**（各行业通用） | 可配置审批链引擎、阶段/门禁引擎、状态机、哈希审计、文档、协作、资源、计划 | 流程管控的"骨架"，任何行业都能用 |
| **研发域插件**（汽车零部件专属） | 汽车零部件阶段模板、APQP/PPAP/OTS/EBOM/8D/功能安全分级、控制点定义 | 行业化的"血肉"，按需启用 |

**关键洞察**：这个工具的"通用"是**管控机制的通用**（审批链+门禁+档案），而非"任务管理"的通用。研发域插件只是给这套通用管控机制填入汽车零部件行业的阶段模板和对象定义。

## 7. 下一步建议（待拍板）

按"先补底座、再填行业"的顺序：

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| P0 | **阶段模板可配置 + 「未批准不得实施」引擎级阻断** | 这是核心机制缺的两块地基 |
| P1 | **「发起→审核→会签→批准」标准审批链模板化** | 把四段式做成开箱即用的默认流程 |
| P2 | **15 年归档层**（归档表 + 只读 + 保留期 + 合规检索） | 合规级档案 |
| P3 | 汽车零部件阶段模板预置 + 交付物绑定审批 | 行业"血肉"填入 |
