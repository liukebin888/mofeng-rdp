## 冲突一：48 控制点强度分布（摘要句 vs 逐行配置表）

### 规格书原文
- **SRS 10.3 摘要句**（SRS.md 第 919 行）：
  > 48 个控制点中，L4 硬阻断 28 个、L3 条件放行 13 个、L2 预警升级 6 个、L1 仅留痕 1 个。
- **SRS 10.3 逐行配置表**（C-01~C-48 每条带 `strength` 字段）逐行统计：**L4 29、L3 10、L2 7、L1 2**。

### 实现口径
`src/domain/controlPoints.ts` 的 `CP_DEFINITIONS` 逐行配置，`strengthDistribution()` 实测返回：
```
{ L4: 29, L3: 10, L2: 7, L1: 2 }
```
即**以逐行配置表为准**（可逐条核对、可复算），与摘要句的 28/13/6/1 存在 4 处出入。

### 分歧本质
摘要句（28/13/6/1）与逐行表（29/10/7/2）不一致。逐行表是「每条控制点独立声明强度」的一手数据源；摘要句是叙述性汇总，可能为早期版本遗留。

### 建议处置
- **采纳逐行表 29/10/7/2**，修订 SRS 10.3 摘要句数字（28→29、13→10、6→7、1→2），使叙述与逐行表一致。
- 若需求方坚持 28/13/6/1，则须明确**哪 1 个 L4 应降级、哪 3 个 L3 应补入、哪个 L2 应升级/移除**，并同步修订对应控制点逐行定义——不接受只改摘要句不改逐行表的「数字对齐」。

### 待需求方决策
- [ ] 确认 48 点强度分布以 **29/10/7/2** 为准，并修订摘要句。

## 冲突二：附录 C 第 13 行兜底 L3 与「CAL≥3 不低于 L2」的缺口

### 规格书原文
- **第 13 行兜底**（SRS.md 第 707 行）：
  > 其余组合 → L3；兜底行：前 12 行未命中的组合一律判 L3，须经分级评审确认；不得默认 L4 或报错阻断。
- **否定性裁定**（SRS.md 第 716 行）：
  > CAL≥3 时，无论是否含自研软件、是否为新架构，一律不低于 L2。
- **CLS-004**（SRS.md 第 726 行）：等级写入基线，改等级需评审。

### 冲突点
存在一个逐行表**无归属行**的组合：`ASIL=QM + CAL=3/4 + 自研软件=否（纯文档/参数变更）`。它：
- 命中第 13 行兜底 → 判 **L3**；
- 但按「CAL≥3 一律不低于 L2」的否定性裁定，L3 字面上**不低于 L2，故不违反该条下限**；
- 真正的问题是：**QM + CAL4 的安全/信息安全特征，判 L3 是否偏轻**，规格书未给出该组合的明确等级。

### 实现口径
`src/domain/grading.ts`：该组合命中第 13 行，返回 `L3`，同时 `CLS-004` 检查项置 `ok:false` 并提示「QM/CAL4/纯文档组合在逐行表无归属行，属规格缺口，按兜底 L3 处理」。**不静默升级**。

### 建议处置
- 若需求方认为「QM + CAL≥3 + 无自研软件」应判 **L2**（信息安全中等级别，对齐第 5 行 `QM/CAL 1~2/是` 的精神），则须在附录 C 逐行表**新增一行**（例如「QM / 3~4 / 否(纯文档) / 任意 / 任意 → L2」），再让实现匹配该行——**不得直接改代码常量绕过逐行表**（CLS-002 禁止另写表达式）。

### 待需求方决策
- [ ] 明确 `QM + CAL≥3 + 无自研软件` 组合的等级（建议 L2），并决定是否在附录 C 增行。

## 冲突三：冻结基线的「不可变」与「变更影响闭包传播」语义

### 规格书原文
- **基线不可变**（SRS.md 第 94、164、249、400 行）：冻结后只读、内容不可变、改删被拒并留审计（BAS-002/BAS-003）；冻结后成员被修改，校验立即报不一致（ARC-008）。
- **变更闭包**（SRS.md 第 276 行）：关键链路含「变更闭包」，即 ECR 影响分析要找出所有受影响对象。

### 冲突点
规格书明确了「冻结对象**不可改**」，但**未明确**：当某个冻结对象被一条 ECR 的影响闭包「命中」时，闭包是否要**继续穿透**该冻结对象去传播其下游，还是**截断**在冻结对象处。

### 实现口径
`src/domain/trace.ts` 的 `closure()`：**全量 BFS，不截断**，命中冻结对象时打 `frozen` 标签并在界面单列（`frozenStopped`），提示「该对象已冻结，变更须走 ECR 解冻流程」。理由：
- 冻结 = **变更受控**（改它须走流程），≠ **信息不可见**；
- 若真截断传播，会把冻结对象**下游未冻结**的对象也一并隐藏，反而制造影响盲区，违背「闭包完整」的目的。

### 建议处置
- 维持「全量传播 + 冻结项打标单列」现状，作为**设计决策**登记；
- 若需求方坚持「冻结即截断」，须明确下游对象的受影响状态如何体现（否则下游失控），并补充 SRS 对应条款。

### 待需求方决策
- [ ] 确认冻结基线在变更影响闭包中采用「全量传播 + 冻结打标」而非「截断」。

## 附三：控制点「同源判定 vs flag 兜底」治理分类（实现方，2026-11-01）

对 48 控制点中依赖 `flag()` 静态兜底的 17 项做系统性治理，按「是否存在可同源的业务实体」分为三类，杜绝「同一规则两套口径」的虚假闭环。

### 第一类：有现成函数/数据却用 flag（已改真实同源）

| 控制点 | 落空点 | 修复 |
|---|---|---|
| C-15 风险关闭 | 只查 residual，未调用 `closeCheck()` 校验高 RPN 双签 | 改为调用 `risk.closeCheck()`，`RiskItem` 增 `signatures` |
| C-18 ECN 验证 | 读静态 flag，与 `change.ts` 关闭校验两套口径 | 改为真实同源判定（上一轮已修） |

### 第二类：业务实体未建模（已补数据模型 + 视图 + 真实同源）

| 控制点 | 判据 | 新增实体 | 判定逻辑 |
|---|---|---|---|
| C-34 阶段复盘 | 目标达成/偏差原因/改进项三要素齐全 | `RetroItem` | 存在「三要素齐备」的复盘记录才 PASS，否则 CONDITIONAL |
| C-35 经验库 | 条目入库并打标签可检索 | `LessonItem` | 条目数>0 且每条 tags 非空才 PASS，否则 CONDITIONAL |
| C-46 纠偏回写 | 措施回写计划 + 偏差重算 | `DeviationItem` | 存在未回写/未重算的纠偏项判 CONDITIONAL |

### 第三类：外部证据 / 人工签署型（flag 登记符合实际，不改代码）

以下控制点判据的载体是系统外合规证据或人工结论，系统内无结构化数据可同源，故用 `flags` 登记实际结论，**不强行代码判定**（否则会制造假同源）：

- C-07 评审三态、C-08 缺陷逃逸率、C-09 返工复验（质量证据，需外部缺陷库）
- C-21 客户签收、C-23 角色到位、C-27 供应商绩效（外部签收/评分）
- C-28/C-47 口径字典一致性（字典由 PMO 外部维护）
- C-30 等保测评、C-31 安全签署、C-33 漏洞（合规/安全外部报告）
- C-36 规则库版本、C-41 成本口径、C-42 储备动用、C-48 回归（管理登记）

> 判定铁律：凡控制点存在可同源的业务实体，必须走真实数据判定；只有外部证据/人工签署型才允许 flag 兜底。该分类已写入 `controlPoints.ts` 的 `flag()` 注释。
