# 架构级立项方案：移动端独立 App + 多空间切换

> 项目：魔程化解研发项目管理工具 MOFENG-RDP
> 文档：PROJECT-PROPOSAL-MOBILE-MULTISPACE
> 版本：v1.0（2026-11-03）
> 状态：待评审（P2 架构级两项，单独立项）
> 依据：SRS V1.4 / 技术方案 V4.0 / Oracle Primavera 对标结论

---

## 0. 摘要

本轮 Oracle Primavera 深度对标的 P0/P1 全部落地、P2 已落地「风险机会型量化」「图文档在线批注」两项。剩余两项——**移动端独立 App** 与 **多空间顶部切换**——因涉及架构级调整（非纯函数引擎可承载），故单独立项。

本方案的关键判断（避免过度设计）：

| 结论 | 依据 |
| --- | --- |
| 移动端**不应**重造原生 App | 现有 `mobilePortal.ts`（断点/弱网排队/缓存）+ `AppLayout.vue` 响应式已就绪，领域层 108 项能力同源复用，重造原生会破坏"规则唯一权威" |
| 多空间**不是**新租户体系 | 现有 `tenant.ts`（集团—子租户 SHARED/SCHEMA/INSTANCE 三模式）已覆盖隔离判定；缺口是**空间维度**（项目组合/工作空间）的 UI 切换与数据隔离，属补齐而非重构 |

两个项目共享同一前置：**前端 shell 层的「上下文切换器」抽象**，因此建议合并立项、分阶段交付。

## 1. 现状盘点（架构级事实）

### 1.1 移动端现状

| 资产 | 位置 | 能力 |
| --- | --- | --- |
| `mobilePortal.ts` | `app/src/domain/` | 三档断点判定（<768 手机 / <1200 平板 / 桌面）、抽屉/折叠/常驻侧栏模式、弱网写入排队去重（同键去重 + 死信 + MAX_ATTEMPTS=3）、缓存时间戳只读判定 |
| `portalConfig.ts` | `app/src/domain/` | 门户配置引擎 |
| `AppLayout.vue` | `app/src/layouts/` | 顶部横向导航条（今日必办/我的任务/我的待办/消息/工时单）+ 响应式适配 + 移动端抽屉侧栏 |
| Vite + Vue3 + Element Plus | `app/` | 零第三方图表库、单文件内联、无外部 CDN 依赖 |

**结论**：移动端「门户层」已 70% 就绪，缺的是「独立交付形态」（PWA 安装、App 壳、推送、原生能力桥接）的选型决策，而非业务逻辑重写。

### 1.2 多空间现状

| 资产 | 位置 | 能力 |
| --- | --- | --- |
| `tenant.ts` | `app/src/domain/` | 集团—子租户两级、三种隔离模式（SHARED 共享表 / SCHEMA 独立 Schema / INSTANCE 独立实例）、`guardTenant` 应用层强制注入、`visibleInTenant` 跨租户过滤、`groupDrillDown` 集团视图下钻白名单 |
| `store/app.ts` | `app/src/store/` | `tenantContext`（tenantId 入口注入）、`visibleProjects`（归属租户项目）、`currentProject`、`guardTenantAccess`（伪造 tenantId 拒绝 + 审计）、`guardGroupDrillDown`（集团视图下钻） |

**结论**：租户级隔离判定已完整（TEN-002/003/004/008 已实现）。缺口是**「空间」这一维度**——当前只有 `projectId` 单项目切换，缺少「项目组合 / 工作空间」层级的顶部切换器与空间级数据隔离（如空间 A 的资源池与空间 B 隔离、空间级 RBAC 边界）。

## 2. 立项一：移动端独立 App

### 2.1 需求定性

用户侧诉求是「移动端独立 App」，但需澄清其本质：是要**可安装、可推送、可离线**的移动交付物，还是要**原生重写**。基于本项目「规则唯一权威（TS 纯函数引擎）+ 零第三方图表 + 同源同权限」的护城河，原生重写是负收益。

### 2.2 技术选型评估（三方案对比）

| 维度 | 方案 A：PWA（渐进式 Web App） | 方案 B：Uni-app / Taro 跨端 | 方案 C：原生（Android/iOS） |
| --- | --- | --- | --- |
| 与现有 Vue3 代码复用 | ✅ 100%（同一份代码） | ⚠️ 需迁移/适配（DSL 差异、组件库 Element Plus 不可用） | ❌ 0%（重写） |
| 规则唯一权威保持 | ✅ 直接复用 TS 纯函数引擎 | ⚠️ 引擎需打包共享，成本高 | ❌ 需 Java/TS 双实现 |
| 离线能力 | ✅ Service Worker 缓存 + 已有弱网排队 | ⚠️ 依赖框架插件 | ✅ 原生最佳 |
| 推送 | ✅ Web Push（iOS 16.4+ 支持，Android 全支持） | ✅ uni-push | ✅ 原生最佳 |
| 安装 | ✅ 添加到主屏 / 应用清单 | ✅ 打壳发布 | ✅ 应用商店 |
| 开发成本 | **低（复用）** | 中 | 高 |
| 维护成本 | **低（单一代码库）** | 中 | 高（三端同步） |
| 应用商店分发 | ❌（iOS 限制 PWA） | ✅ | ✅ |
| 国密 TLS / 等保合规 | ✅ 复用现有网关 | ⚠️ 需适配 | ⚠️ 需适配 |

**推荐：方案 A（PWA）为主，方案 C（原生壳）为可选延展。**

理由：
1. 本项目核心纪律是「TS 纯函数引擎为规则唯一权威」，任何重写/跨端迁移都会引入「两套口径」，直接违反 ARC-001。
2. 用户当前场景是研发管理平台（内部/企业使用为主），PWA 的「添加到主屏」即可满足"独立 App"的体感，无需上架商店。
3. `mobilePortal.ts` 已铺好断点/离线排队/缓存地基，PWA 是其自然延伸。

### 2.3 建议实施路线（PWA）

| 阶段 | 交付物 | 关键点 |
| --- | --- | --- |
| M1：PWA 基线 | `manifest.webmanifest` + `service-worker.ts`（vite-plugin-pwa）+ 图标组 + 全屏/主题色 | 离线缓存 shell + 关键路由；SW 版本化与缓存失效策略 |
| M2：离线写入闭环 | 打通 `mobilePortal.ts` 弱网排队 → SW 后台同步（Background Sync）| 复用现有 `enqueueWrite/settleWrite`，接入 `sync` 事件 |
| M3：Web Push | 订阅/推送 token 管理 + 后端推送服务 + 消息落地到现有 `messageCenter` | 复用现有消息中心引擎，推送与站内信同源 |
| M4：移动端体验收口 | 触控目标尺寸、底部 Tab 导航、移动端表单控件、离线只读标识（`缓存时间戳`已有）| e2e 在移动视口跑冒烟 |

### 2.4 可延展：原生壳（仅当需要应用商店分发时）

若未来需上架商店，采用 **Capacitor**（而非 Cordova/纯原生）包一层：`Capacitor` 直接包裹现有 `dist/`，WebView 加载 PWA 产物，原生能力（相机、文件、通知）通过插件桥接，业务逻辑仍 100% 走 TS 引擎。此延展不阻塞 PWA 主线。

## 3. 立项二：多空间顶部切换

### 3.1 需求定性

「多空间」的本质是引入一个**介于租户与项目之间的聚合维度**（项目组合 / 工作空间），支持用户在顶部一键切换，且各空间之间数据隔离、权限独立。

### 3.2 数据隔离设计

#### 3.2.1 维度模型（空间层级）

```
租户 Tenant（已实现，tenant.ts）
 └─ 空间 Space（新增：项目组合/工作空间，可多个）
      └─ 项目 Project（现有 projectId）
```

**新增实体**（`types.ts` + 新引擎 `spaceEngine.ts`，纯函数）：

```ts
export interface Space {
  id: string            // 空间唯一标识，如 'SP-001'
  tenantId: string      // 归属租户（继承现有租户隔离）
  name: string          // 空间名，如「九甲科技」「中科电安」
  code: string          // 空间编码
  roleBoundary: string[] // 空间级可见角色白名单（RBAC 边界）
  // 空间级隔离资源归属
  resourcePoolIds: string[]   // 归属空间的资源池
  costSubjectIds: string[]    // 归属空间的成本科目
}

export type SpaceContext = {
  tenantId: string
  spaceId: string
  roleCode: string
}
```

#### 3.2.2 隔离规则（复用现有 tenant 引擎口径，禁止另起一套）

| 规则 | 落点 | 复用 |
| --- | --- | --- |
| 空间归属租户校验 | `guardTenant` 扩展：空间必须归属上下文 tenant，否则 `SPACE_FORGED` 拒绝 | `tenant.ts guardTenant` |
| 跨空间资源不可见 | `visibleInSpace(ctx, items)`：`items.spaceId` 不匹配 → 过滤（不泄露存在性）| 对齐 `visibleInTenant` 语义 |
| 空间级 RBAC 边界 | 空间内仅 `roleBoundary` 角色可见；越界角色访问 → 拒绝 + 审计 | `rbac.ts` + `audit.ts` |
| 空间切换留痕 | 切换空间 → `log('SWITCH_SPACE', ...)` 审计 | `audit.ts` |

#### 3.2.3 数据隔离面矩阵（对齐 SRS 7.2 三面）

| 隔离面 | 机制 |
| --- | --- |
| 应用层 | 请求入口强制注入 `spaceId` 上下文（同 tenantId 注入模式）；伪造 spaceId → 403 |
| 数据库层 | 共享表：查询统一附加 `space_id` 条件（后端 MyBatis 拦截器扩展，对齐现有多租户拦截器） |
| 缓存层 | 键前缀含 `tenant:space`，禁止跨空间复用同键 |

### 3.3 顶部切换器 UI 设计

- 位置：现有 `.worktop` 顶部导航条（`AppLayout.vue`）最左侧，作为上下文切换器。
- 形态：`租户 > 空间 > 项目` 三级下拉/面包屑级联切换。
- 交互：切换空间 → `spaceContext` 更新 → `visibleProjects` 收窄为该空间项目 → 视图整体刷新。
- 权限：无空间权限的选项置灰 + 提示（复用 `guardSpaceAccess`）。

### 3.4 建议实施路线

| 阶段 | 交付物 |
| --- | --- |
| S1：领域引擎 | `spaceEngine.ts`（Space 实体 + guardSpace + visibleInSpace + spaceDrillDown）+ 单测 |
| S2：store + seed | `spaceContext` / `spaces` / `visibleProjects` 收窄 + seed 播 2 空间 |
| S3：顶部切换器 | `AppLayout.vue` 三级级联切换 + 审计留痕 |
| S4：后端隔离 | MyBatis `space_id` 拦截器扩展 + 缓存键前缀 |
| S5：e2e | 跨空间越权/伪造 spaceId 拒绝、切换后数据收窄、审计留痕 |

| G3：推送闭环 | Web Push + 消息同源 | 端到端推送验证 |

### 4.1 已拍板决策（2026-11-03，用户体验优先）

| # | 决策项 | 结论 | 理由 |
| --- | --- | --- | --- |
| D1 | 移动端形态 | **PWA + Capacitor 壳** | 体验优先：即时可用 + 可上架商店 + 原生推送/离线/桌面图标最完整，业务仍走 TS 引擎 |
| D2 | 空间语义 | **项目组合** | 契合「九甲科技」「中科电安」多项目集场景，切换体感自然、边界清晰 |
| D3 | 排期 | **串行** | 每里程碑端到端实测收口，避免共享前置撕裂导致半成品上线 |
| D4 | 商店分发 | **需要** | 因 D1 含 Capacitor 壳，为原生推送/离线/商店分发服务 |

### 4.2 体验优先设计承诺（贯穿全流程）

1. **移动端交互**：底部 Tab 导航、触控目标 ≥ 44px、移动端表单控件、离线只读标识（复用 `mobilePortal.ts` 缓存时间戳）——真机手感而非"网页缩放"。
2. **空间切换**：顶部三级级联（租户>空间>项目）即时刷新 + 无权限选项置灰提示 + 切换审计留痕。
3. **推送体验**：Web Push + 原生推送（Capacitor）同源到现有 `messageCenter`，站内信与推送一体。
4. **验证门槛**：每里程碑要求移动视口 e2e 冒烟 + Lighthouse PWA 达标，不达标不进入下一门禁。

## 5. 风险与边界

| 风险 | 应对 |
| --- | --- |
| PWA 在 iOS 上限制（无后台同步、推送需 16.4+）| 明确 iOS 降级策略：缓存只读 + 前台同步 |
| 空间维度引入后，现有 `visibleProjects` 语义变更可能影响 108 路由探针 | 空间收窄作为新过滤层叠加，不改变 tenant 过滤结果，探针回归 |
| 跨端/原生壳若失控会破坏「规则唯一权威」| 硬约束：任何壳方案业务逻辑仍走 TS 引擎，原生仅做能力桥接 |

**硬约束（贯穿两项目）**：
- 规则唯一权威：隔离判定仍以 `tenant.ts`/新 `spaceEngine.ts` 纯函数为单一来源，禁止在视图/store 里自造比较逻辑。
- 只读/导出零业务写入：切换空间、移动端缓存均不改业务数据。
- 数据变更必须快照 + 回滚 + 审计留痕。
- 六门禁全链路实测 + 回退验证（已知违规样本）后方可 commit。
